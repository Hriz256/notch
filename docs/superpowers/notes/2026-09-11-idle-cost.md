### 5. Thread state — proof that nothing is ticking

```bash
sample $(pgrep -x Notch) 15 -f sample.txt
```

The process has exactly two threads, and every one of the 11 869 samples on each thread
is blocked in `mach_msg2_trap`:


No dispatch-worker threads, no CoreAudio `caulk` threads, no CoreAnimation render thread.
`VisualizerBars`, `MarqueeText`, `AudioOutputMenu` and the `MusicViewModel` 1 Hz tick all
live inside presentation views, and with an empty queue `SurfaceView` never instantiates
them, so there is nothing left alive to animate.

### 6. Memory

```bash
footprint -p $(pgrep -x Notch)
footprint -p $(pgrep -x NotchHelper)
vmmap --summary $(pgrep -x Notch)
```

```
Notch [43334]:       Footprint: 17 MB    phys_footprint_peak: 18 MB
NotchHelper [43336]: Footprint: 4145 KB  phys_footprint_peak: 4529 KB
```

**On reading the RSS number.** `ps -o rss` reports ~79 MB for Notch, which looks like it
blows the 40 MB budget, but it does not: RSS counts resident *shared* read-only pages
mapped from the dyld shared cache (AppKit, SwiftUI, CoreFoundation …), which every app on
the system maps and which are not charged to Notch. `vmmap --summary` separates them:

```
Physical footprint:         17M
ReadOnly portion of Libraries: Total=1.8G resident=761.7M(42%) swapped_out_or_unallocated=1.0G(58%)
Writable regions: Total=291.1M written=17.9M(6%) resident=19.0M(7%) swapped_out=0K(0%)
```

`phys_footprint` — the figure Activity Monitor shows as "Memory" and the one jetsam
accounts against — is 17 MB, comfortably inside the 40 MB budget. The same holds for the
helper: 14.4 MB RSS, 4.1 MB footprint.

## Notes for the future

- An earlier run of the same audit against `e3de593` measured a 25 MB footprint with a
  102 MB peak and ~0.16 % average CPU, because that instance had been driven into the
  expanded view by hand: opening it loads Metal (`AGXMetalG17X`) and CoreAudio (the
  `AudioOutputMenu` device enumeration brings in the CoreAudio HAL and its `caulk`
  worker threads), and those stay resident afterwards. That is expansion cost, not idle
  cost — a never-expanded process stays at 17 MB with two threads. Worth remembering if
  the footprint budget is ever tightened: the CoreAudio/Metal load is the biggest
  one-way step.
- `HoverMonitor` spawns a `Task { @MainActor … }` per global `.mouseMoved` event. That
  costs nothing while the pointer is still (which is what "idle" means here), but it is
  the one place that does per-event allocation, so it is where to look first if hover
  ever shows up in a CPU profile.
